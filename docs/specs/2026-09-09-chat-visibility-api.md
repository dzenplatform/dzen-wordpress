# Task: Скрытие чатов в админке Dzen Chat и API

Статус: серверная постановка; реализация сервера не входит в изменение WordPress.

## Goal

Администратор может скрыть диалог из основного списка и вернуть его через
фильтр «Скрытые». WordPress и админка Dzen Chat показывают одно состояние.
Чаты и сообщения остаются на сервере Dzen Chat как история, связанная с биллингом.

## Context

- `chat/models/data.py`: `Chat`, `ChatMsg`, `project_id`, сообщения и учёт токенов.
- `chat/views/projects/chats.py`: `history_list`, `history_detail`, фильтры,
  подготовка сообщений и источников ответа.
- `chat/routes.py`: проектные маршруты истории и публичный API.
- [Контракт WordPress](../contracts/dzen-chat-api-v1.md).

## Current Behavior

В проверенном коде нет отдельного состояния скрытия и API для его изменения.
Пользователь подтвердил: удаление чатов не предусматривается. Прежнее предложение
`DELETE /chats/{id}` отменено. Локальную копию чатов в WordPress не создаём.

## Target Shape

Скрытие — общее состояние диалога в проекте, не персональный фильтр администратора
и не удаление. Существующие диалоги по умолчанию видимы. Сервер хранит состояние,
дату, автора действия и монотонную `visibility_version`; способ хранения выбирает
серверная реализация. Аудит различает пользователя Dzen Chat и API-интеграцию.

### Админка Dzen Chat

- Основной список показывает видимые диалоги. Фильтр: видимые / скрытые / все.
- Поиск, фильтры по датам и виджетам, пагинация применяются вместе с видимостью.
- В строке и карточке диалога есть «Скрыть» или «Вернуть в список».
- Скрытая карточка доступна по прямому URL при сохранённых правах, с отметкой
  «Скрыт». Скрытие не завершает активный диалог и не запрещает новые сообщения;
  новые сообщения не меняют состояние скрытия.
- Подтверждение операции объясняет, что переписка и биллинговые данные сохраняются.
- Счётчик списка соответствует выбранному фильтру. Биллинговые и общие показатели
  использования продолжают учитывать скрытые чаты.

### API, используемый WordPress

`GET /api/v1/chats?visibility=visible|hidden|all&q=...&date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&widget_id=...&cursor=...&limit=20`

Ответ: `items`, `next_cursor`. Элемент: `id`, `title`, `preview`, `created_at`,
`updated_at`, `widget_id`, `hidden`, `hidden_at`, `visibility_version`,
`message_count`. Даты — UTC; границы date_from/date_to включают календарные дни
UTC. Стабильная сортировка по created_at и ID. Пустой результат — успешный список.

`GET /api/v1/chats/{id}` возвращает эти же поля и разрешённые метаданные.
Скрытая карточка не превращается в 404 только из-за скрытия.

`PATCH /api/v1/chats/{id}/visibility`

```json
{"hidden": true, "expected_version": 3}
```

Ответ 200: `id`, `hidden`, `hidden_at`, `visibility_version` (новая версия).
Для восстановления `hidden=false`. При конфликте версии — 409 с безопасным
кодом `visibility_conflict`; клиент перечитывает состояние. Операция
идемпотентна по ключу запроса, одинаковое повторное действие не создаёт второе
событие биллинга и не меняет сообщения. Не использовать `DELETE` или toggle
без явного целевого состояния.

Scope чтения — `chats:read`, изменения — `chats:visibility:update`.
`project_id`/область сайта выводятся из credentials. Нужна проверка каждого
chat ID и источника в разрешённой области, включая скрытую историю.

### Источники сообщений для WordPress

WordPress показывает у сообщения источники ответа и предоставляет два действия:
просмотр безопасного текста/фрагмента в собственном экране WP и внешнюю ссылку
на оригинал. Эти методы входят в общий API интеграции и должны сохранять доступ
к источникам скрытого диалога при тех же правах.

`GET /api/v1/chats/{id}/messages?cursor=...&limit=50` → `items`, `next_cursor`.
Сообщение: `id`, `role` (user/assistant), `text`, `created_at`, `vote`, `sources`.
Источник: `id` (непрозрачная ссылка конкретного сообщения), `title`, `url`
(публичный HTTP(S) или null), `available`.

`GET /api/v1/chats/{chat_id}/messages/{message_id}/sources/{reference_id}` →
`id`, `title`, `url`, `content`, `content_kind` (excerpt/document), `available`,
`unavailable_reason` (если недоступен), `captured_at` (если известен).
`content` — обычный текст разрешённого источника, не HTML страницы/iframe и не
`full_context`/system prompt. Для отсутствующего или отозванного источника —
явная недоступность; приватный URL/токен не должен попасть во внешнюю ссылку.
Снимок цитаты показывается как снимок, текущее содержимое — как текущее.
Проверяются вся цепочка chat → message → reference и актуальное право просмотра.

## Guard Rails

- Никаких DELETE для Chat/ChatMsg, удаления токенов, изменения биллинговых записей,
  каскадов и сокращения срока хранения в рамках скрытия.
- Не фильтровать скрытые чаты из расчёта оплаты, выгрузок учёта и общего usage.
- Не хранить переписку и содержание источников в WordPress options/transients/БД.
- Не выдавать существование или содержание чата другого проекта/сайта.
- Не скрейпить HTML админки Dzen Chat и не передавать её пользовательские cookies.
- Не менять текущий checkout с чужими правками; отдельная ветка/worktree.

## Iterations

1. Зафиксировать DTO/scopes, состояние, авторство и версию; тестировать изоляцию.
2. Добавить серверную операцию и GET-фильтр; проверить гонку и повтор запроса.

4. Проверить источники, клиента WordPress и неизменность биллинговой истории.

## Verification

- Скрытый чат исчезает только из видимого списка; поиск hidden/all находит его.
- Восстановление возвращает чат; состояние совпадает между WP и Dzen Chat.
- Скрытие/восстановление не меняет количество Chat/ChatMsg, суммы токенов,
  биллинговые события и стоимость. Сравнить значения до/после на стенде.
- Новое сообщение в скрытом чате сохраняется и учитывается без его раскрытия.
- Два конкурентных PATCH с одной версией: один успех, второй конфликт;
  повтор идемпотентного запроса возвращает тот же результат.
- Чужой проект/сайт/сообщение/источник и недостаточный scope дают отказ.
- Источник открывается текстом в WP и по безопасной внешней ссылке; удалённый
  источник имеет понятный результат. Скрипт/небезопасный URL не исполняется.
- 401/403/409/429/5xx не отображаются как успешное скрытие; при сбое нет локальной
  подмены состояния. Проверить CSRF и права в обеих административных панелях.
