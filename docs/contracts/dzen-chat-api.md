# Публичный API Dzen Chat: контракт WordPress 0.4

Проверено 11 сентября 2026 по работающему локальному сервису, Swagger
`https://local.dzenchat.com/api-docs/` и обработчикам `chat/api/`.
Серверная задача: `01a086d7-18f2-73e1-99b0-b59d123f2da5`.
Этот документ заменяет предложение Integration API v1 из версии 0.1.
Маршруты используются без номера версии, scopes и HMAC-подписи.

## Регистрация и транспорт

`GET /auth/add` получает `type=wordpress`, HTTPS `site_url`, `redirect_uri`,
`state`, `code_challenge`, `code_challenge_method=S256`.
Callback WordPress — `/wp-admin/admin-post.php?action=dzen_chat_authorize`
в пределах того же сайта. Проверяются сессия администратора, state, срок попытки,
адрес сайта и origin сервиса. Код предъявляется один раз.

`POST /auth/exchange/` принимает JSON `code`, `code_verifier`, `redirect_uri`.
Ответ 200 содержит `client_id`, `client_secret`, `site_source_id`.
Идентификаторы проекта и интеграции из ответа не выдумываются.
Полная проверка регистрации описана в [отчёте](../verification/2026-09-11-registration.md).

Управление: `Authorization: Bearer <client_id>.<client_secret>`, префикс `/api`.
Проект и доступные объекты определяет сервер по клиенту. Произвольный project_id
не передаётся. WordPress проверяет TLS, не пересылает cookies, не следует
редиректам, ограничивает размер ответа 2 MiB. Все URL запросов строятся плагином,
а не берутся из ответа сервера. История и содержание источников не кешируются в WP.

## Реализованные методы, используемые плагином

Все ID непрозрачны. Коллекции имеют форму `{items: [...]}`.
Отсутствующее поле или непроверенный ответ не подтверждает выполнение изменения.

| Метод | Реальный контракт |
| --- | --- |
| GET /api/widgets | Все доступные виджеты; без query |
| POST /api/widgets | Только name, 1–128 символов; ответ 201 |
| GET /api/widgets/{id} | id, name, code, is_enabled, suggestions_enabled, trigger_templates, appearance |
| PATCH /api/widgets/{id} | name, is_enabled, suggestions_enabled; ответ с подтверждёнными полями |
| POST /api/update | Только JSON url; ответ 202 означает постановку обхода |
| GET /api/pages?limit=100 | Последние обновлённые страницы; только limit 1–100 |
| GET /api/pages/{id} | id, url, title, source_id, status, status_error, has_triggers, updated_at |
| GET /api/sources | Назначенные клиенту источники; без query |
| GET /api/sources/{id} | id, title, url, is_paused, enable_triggers, blocked_reason, last_reindexed_at |
| GET /api/files | Файлы базы знаний; без query |
| GET /api/files/{id} | id, name, content, status, status_error, size_bytes, updated_at |
| GET /api/chats?limit=100 | Последние созданные диалоги; только limit 1–100 |
| GET /api/chats/{id} | id, created_at, updated_at, visitor, widget_code, feedback |
| GET /api/chats/{id}/messages?limit=100 | Первые сообщения; id, role, text, created_at, vote, guardrail_triggered, guardrail_stage |

В текущих списках страниц, диалогов и сообщений нет cursor/offset.
Серверные фильтры поиска, даты, источника и виджета отсутствуют.
Плагин применяет доступные фильтры к полученным 100 объектам и сообщает об этом.
В длинном диалоге не объявляется полная загрузка после первых 100 сообщений.

Виджеты используют настоящий loader `/widget/{code}`.
WordPress выводит один `<div id="chat-chat"></div>` до скрипта в footer.
Загрузчик создаёт кнопку и iframe; положение iframe не обязано быть внутри mount.
В кеше остаются только публичные поля виджета. TTL — 300 секунд, повтор после
ошибки — через 60 секунд. Сохранение в WP обновляет состояние сразу.

Сообщения выводятся только для ролей user/assistant, с экранированием текста.
Внутренние промпты не отображаются. Удаление/изменение истории блокируется
клиентом до HTTP. Метаданные источника, содержимое файла и ссылки на оригинал
доступны внутри WP, но цитаты отдельного ответа в API сообщений отсутствуют.

## Обновление контента

WordPress отправляет только публичные page/post без пароля. Новый черновик,
товар и изначально защищённая запись не создают запроса публикации.
При подключении, обновлении с 0.3 и повторной активации начинается сверка;
она обходит по 50 записей за проход, транспорт выполняет до 10 событий.

Сохранение создаёт локальное событие и не ждёт HTTP. В очередь не копируется
текст страницы: сохраняются ID записи/клиента, URL, предыдущий URL и ревизия.
Историческое имя столбца integration_id сохранено для совместимости таблиц;
теперь он содержит client_id и используется только как привязка очереди.
События предыдущего клиента не передаются после переподключения к другому.

Тело запроса:

~~~json
{"url":"https://wp-site.com/example/"}
~~~

Подтверждение:

~~~json
{"status":"ok","action":"queued","url":"https://wp-site.com/example/","final_url":null,"message":"Page update queued"}
~~~

Статус accepted в WP означает только передачу URL. Отдельных operation IDs,
polling и событий удаления у этого API нет. Процесс использует существующий
crawler Dzen Chat. Фактическое состояние страницы читается через /api/pages.
При проверке подтверждения сравниваются нормализованные URL: учитываются
завершающий слеш корня, порт по умолчанию, IDN и Unicode. Другой host, порт,
путь или query не подтверждает исходный запрос.

При изменении permalink отправляются старый и новый URL. При снятии публикации,
защите паролем, переносе в корзину и удалении отправляется ранее публичный URL
на повторный обход. **Это не команда исключения и не гарантия удаления из
поиска.** Сервер может обработать 404/soft-404 позднее; поведение удаления ещё
нужно согласовать и проверить отдельно.

Временная сеть, HTTP 429 и 5xx повторяются с ограниченной задержкой и учётом
Retry-After, максимум шесть попыток. Успешно принятые события повторно не
опрашиваются. При постоянной ошибке доступен ручной повтор и сверка.
WP-Cron либо системный планировщик должен вызывать задания WordPress.

## Чего не хватает для всей согласованной функции

| Требование | Недостающая серверная возможность |
| --- | --- |
| Скрыть/восстановить диалог | Обратимое состояние видимости, фильтр списка и метод изменения; без удаления сообщений, токенов и биллинга |
| Читать источник ответа в WordPress | Список ссылок/цитат сообщения и разрешённый текст источника с проверкой принадлежности диалогу |
| Искать по всей истории и индексу | Пагинация и серверные фильтры; продолжение списка сообщений |
| Включать триггеры отдельной страницы | Чтение и запись политики для URL сайта, в том числе до появления документа в индексе |
| Проверять оплату и активность проекта | Явное серверное состояние с причиной ограничения и поведением операций |
| Убирать закрытый/удалённый материал из ответов | Подтверждаемое исключение URL из retrieval и дальнейшего обхода, с возможностью восстановить публикацию |

Скрытие и источники истории поставлены в [Dzen Chat #14](https://github.com/xen/dzen.chat/issues/14).
Это список необходимых дополнений, а не утверждение о существовании методов.
Точные пути и DTO следующих действий должны быть согласованы в серверной задаче.
Список файлов сейчас возвращает content каждого файла. Для больших баз знаний
нужен список метаданных без содержимого и пагинация: ответы больше 2 MiB плагин
отклоняет целиком, чтобы не загружать неограниченный объём в память WordPress.

Успешный запрос, активный API-клиент и is_paused=false у источника не доказывают
оплату проекта. Плагин не выводит биллинговое состояние из названия тарифа или
отсутствия ошибки. Публичную выдачу ответов контролирует сам Dzen Chat.

## Проверка и границы

[Отчёт 0.4.0](../verification/2026-09-11-full-integration.md) разделяет настоящую
проверку на локальном Dzen Chat и изолированные контрактные тесты.
Fixture повторяет только перечисленные формы ответов; недостающие операции
не имитируются. Fixture, сертификаты и dev overlay не входят в ZIP.
Основной проект Dzen Chat и production этой итерацией не изменяются.
