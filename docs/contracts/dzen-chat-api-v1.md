# Требования WordPress-плагина к API Dzen Chat

Дата: 2026-09-09. Состояние: **контракт клиента WordPress 0.1.0**. Плагин реализует
этот контракт по указанию пользователя, как если бы API уже существовал.
Это не подтверждение доступности серверного API.
В текущем коде найден `POST /api/update`; остальные методы ниже требуют
реализации или выделения из существующей административной логики.

Основная постановка: [плагин WordPress](../specs/2026-09-09-wordpress-plugin.md).

## Подключение

### GET /auth/add и POST /auth/add

Входные параметры начала: `host`, `type=wordpress`, `site_url`, `redirect_uri`,
`state`, `code_challenge`, `code_challenge_method=S256`. Тип задаётся реестром
поддерживаемых интеграций; произвольный тип отклоняется. GET показывает
подтверждение, при необходимости после входа; POST проверяет CSRF, выбранный
проект и право выдавать доступ.

Страница сообщает: «Вы хотите добавить интеграцию Dzen Chat на сайт {host},
который работает под управлением WordPress». Проект создаётся с названием host
и источником site_url либо выбирается существующий. Для существующего проекта
согласие явно перечисляет виджеты/диалоги сайта и дополнительное чтение статусов
источников. Создание проекта, источника и клиента нельзя дублировать повторным POST.

Ответ браузеру: callback с `code`+`state`; при отказе — `error=access_denied`+
`state`, без внутренней диагностики. После неверного callback редирект отсутствует.
Точный URL связывается с запросом авторизации, кодом и интеграцией. HTTPS,
PKCE S256, короткий TTL, хеш кода, атомарное погашение, безопасный выход при
потере сессии. Нельзя доверять только переданному `host` для выдачи прав.

### POST /api/v1/integrations/exchange

Серверный JSON-запрос: `code`, `code_verifier`, `redirect_uri`.

Пример формы ответа (значения демонстрационные):

```json
{
  "integration_id": "integration-example",
  "client_id": "chatid-example",
  "client_secret": "<выдаётся только в этом ответе>",
  "project": {"id": "project-example", "title": "wp-site.com"},
  "site_url": "https://wp-site.com/",
  "site_source_id": "source-example",
  "scopes": ["integration:read", "documents:read", "documents:write"],
  "api_version": "1"
}
```

Реальный набор scopes определяется согласием. Ответ `Cache-Control: no-store`.
Клиент появляется в существующем списке API clients с названием WordPress и
доменом. `client_id/client_secret` относятся только к этой интеграции.
Повтор, гонка, истечение или неверная привязка дают отказ; секрет не выдаётся
второй раз. Утраченный ответ требует повторного подключения с отзывом
незавершённого клиента, без автоматического создания дублей проекта/источника.

## Обязательные группы методов

Префикс всех следующих методов — `/api/v1`. IDs непрозрачны для WordPress.

| Метод и ресурс | Назначение | Существенные данные/ограничения |
| --- | --- | --- |
| `GET /integration` | Проверка подключения и состояния | integration/project/site, scopes, версия, capabilities, ограничения, разрешённые операции, время проверки и безопасные action links |
| `DELETE /integration` | Отзыв подключения | Только текущий клиент и его интеграция; проект/источники/другие клиенты сохраняются |
| `GET /widgets` | Доступные сайту виджеты | ID, имя, enabled, публичный script URL/code, источники и разрешённые поля |
| `POST /widgets` | Создать виджет | Название, доступные источники, параметры; привязка к сайту и проекту из credentials |
| `GET /widgets/{id}` | Настройки виджета | Публичные настройки без внутренних secret и системной конфигурации |
| `PATCH /widgets/{id}` | Управлять виджетом | enabled, имя, приветствие, оформление, источники и прочие явно согласованные поля; контроль версии |
| `GET /documents` | Список документов | source/status/url/search, cursor/limit; ID, external_id, URL, заголовок, безопасная ошибка и даты |
| `GET /documents/{id}` | Состояние документа | Статус обработки, причина исключения/ошибки, даты, применённая версия; полного технического контекста нет |
| `POST /document-events` | Обновление или удаление материала | event_id, external_id, revision, action, url, previous_url; 202 с operation_id и идемпотентность |
| `GET /operations/{id}` | Проверить итог фоновой команды | queued/running/succeeded/failed/superseded, результат, код безопасной ошибки, даты |
| `GET /page-policies` | Политики триггеров | По external_id или URL: inherit/enabled/disabled, эффективное состояние и причина |
| `PUT /page-policies/{external_id}` | Включить/выключить триггеры страницы | Политика действует до индексации и после изменения URL; изоляция по integration |
| `GET /chats` | История общения | cursor/limit, date_from/date_to, widget_id, q, visibility=visible/hidden/all; ID, даты, preview, message_count, hidden, visibility_version |
| `GET /chats/{id}` | Карточка диалога | Разрешённые метаданные сайта и виджета; проверка области интеграции |
| `GET /chats/{id}/messages` | Сообщения | Пагинация, user/assistant, текст, время, публичные цитаты и оценки; system/full_context исключены |
| `GET /chats/{id}/messages/{message_id}/sources/{reference_id}` | Источник в админке WP | Разрешённый текст/цитата, название, публичный URL, доступность и дата снимка; полная проверка цепочки принадлежности |
| `PATCH /chats/{id}/visibility` | Скрыть/восстановить | hidden boolean, expected_version integer; ответ id/hidden/hidden_at/visibility_version; scope chats:visibility:update |
| `GET /sources` | Состояние источников | Основной сайт и явно разрешённые дополнительные источники; тип, имя, состояние, счётчики, даты |
| `GET /sources/{id}` | Подробность состояния | Пауза, последняя/следующая индексация, ошибки доступа/обработки; без паролей и закрытых параметров |

Удаление чатов и изменение сообщений запрещены: это серверная биллинговая история.
Плагин отвергает такие операции до отправки HTTP. Скрытие общее для проекта,
обратимое и не изменяет сообщения, учёт токенов или оплату. Основной список
показывает видимые чаты; скрытые доступны через фильтр и прямую карточку.
История и содержание источников не сохраняются в WordPress. Источник открывается
экранируемым текстом на отдельном экране WP и отдельной безопасной HTTP(S)-ссылкой
на оригинал. Точный DTO и приёмка: [серверный тикет #14](https://github.com/xen/dzen.chat/issues/14).

Для виджетов базовое удаление заменено отключением в предлагаемом MVP; если
нужно удаление, оно отдельно фиксируется со scope и поведением существующих
вставок. Для политик страниц можно выбрать другую форму пути, но управление
только по ID уже проиндексированного документа не покрывает исходный сценарий.

## Статус проекта и возможности

Предлагается ответ `GET /integration` с независимыми полями:

```json
{
  "integration": {"id": "integration-example", "status": "active"},
  "project": {
    "id": "project-example",
    "title": "wp-site.com",
    "status": "restricted",
    "reason_code": "payment_required"
  },
  "allowed_operations": {
    "widget_answers": false,
    "documents_upsert": false,
    "documents_delete": true,
    "chats_read": true
  },
  "checked_at": "2026-09-09T12:00:00Z"
}
```

Поля и разрешения примера — **предложение**, реального источника статуса оплаты
в проверенном коде нет. Серверная задача должна найти существующий источник
или явно согласовать минимальную модель состояния. Флаг активности API-клиента
не является ответом на вопрос об оплате проекта. Статусы источника — отдельно.

WP не выводит разрешения из названия тарифа. Возобновление после оплаты,
блокировка, отзыв клиента и неизвестное состояние проверяются раздельно.
Даже при устаревшем кэше WP выдачу ответа блокирует сам сервис.

## Аутентификация и изоляция

- Проект и интеграция выводятся из credentials. Переданный `project_id` не
  расширяет права. Для любого дочернего ID проверяются проект, интеграция и scope.
- Данные истории ограничиваются виджетами этого сайта. Исторический диалог без
  доказуемой привязки к сайту не становится автоматически доступным интеграции.
  Дополнительные источники доступны только в разрешённом объёме статусов.
- Минимальные scopes: `integration:read`, `integration:revoke`, `widgets:read`,
  `widgets:write`, `documents:read`, `documents:write`, `triggers:read`,
  `triggers:write`, `chats:read`, `chats:visibility:update`, `sources:status:read`.
- Секрет передаётся только при обмене кода. Последующие запросы используют
  согласованную подпись; существующая HMAC-подпись `/api/update` не подходит
  для запросов, содержащих другие поля и действия.
- Клиентская версия фиксирует канонизацию ниже. Подпись
  покрывает HTTP method, точный path/query, SHA-256 тела, client_id, timestamp,
  случайный nonce и ключ идемпотентности. Обязательны проверка часов, защита
  повторов, константное сравнение, версия схемы и rate limits.
- Ретрай события сохраняет тело и event_id, но имеет новые timestamp, nonce и
  подпись. Повтор транспорта не выдаётся за новую предметную операцию.
- HTTPS проверяется с обеих сторон. Подписанные запросы не следуют редиректам;
  хост API не берётся из произвольного параметра ответа. Production API —
  `https://chat.dzen.dev`; локальный адрес конфигурируется только для разработки.

## Доставка и состояние документов

Пример события:

```json
{
  "event_id": "example-uuid",
  "external_id": "wp:post:123",
  "revision": 7,
  "action": "upsert",
  "url": "https://wp-site.com/new-page/",
  "previous_url": "https://wp-site.com/old-page/"
}
```

Пользователь подтвердил: синхронизируются только публичные страницы и записи
WordPress (`page`/`post`). Товары — будущая отдельная интеграция. Начальная сверка
и новые события не включают товары и остальные типы; новый WP-источник соблюдает
это ограничение также при обходе sitemap и ссылок. Существующие независимые
источники проекта не перенастраиваются автоматически.

`integration_id` определяется аутентификацией; `revision` монотонна для объекта.
`delete` является явным удалением, включая индекс, производные данные и
применимые кэши, а не просьбой когда-нибудь проверить HTTP 404. Удаление повторно
отсутствующего объекта успешно и не затрагивает объекты другой интеграции.
Потеря публикации должна убирать страницу из выдачи и сохранять tombstone.

События обрабатываются в версии объекта: повтор UUID с тем же телом возвращает
ту же операцию; тот же UUID с другим телом — конфликт. Запоздалый `upsert` после
`delete` не индексирует старый материал. Повторный обычный обход источника
соблюдает tombstone и исключения WP. Новый разрешённый `upsert` с большей версией
может восстановить опубликованный материал.

`202` означает запись команды для выполнения. Статус `succeeded` появляется
после фактической индексации/удаления и обновления выдачи. Старый и новый URL
при переименовании обрабатываются одной предметной командой; до завершения
статус явно промежуточный. Backend использует существующий crawler lifecycle,
проверяет URL/источник и не создаёт вторую систему извлечения текста.

## Формат ответов и ошибки

Все списки ограничены `limit` с максимумом, имеют стабильный порядок и
непрозрачный `next_cursor`; фильтры проверяются. Даты — UTC RFC 3339.
История сообщений и документные списки не возвращаются целиком без пагинации.
Конкурирующие изменения виджетов/политик требуют согласованной версии/ETag.

Ошибка: `error.code`, безопасный `error.message`, `request_id`; для валидации
допустимы поля, для ограничения — причина и разрешённое действие. В ответах нет
traceback, SQL, секретов источников или текста внутренних промптов.

| HTTP | Смысл для WordPress |
| --- | --- |
| 400/422 | Неверный запрос; исправление данных |
| 401 | Неверная/отозванная аутентификация; переподключение |
| 403 | Недостаточные права или ограничение проекта с отдельным reason_code |
| 404 | Объект отсутствует или не принадлежит разрешённой области |
| 409 | Конфликт версии/идемпотентности/обмена кода по согласованному протоколу |
| 429 | Ограничение частоты, `Retry-After` |
| 503 | Временная недоступность; операция не объявляется выполненной |

Точные ошибки обмена кода и полной схемы подписей — блокирующая часть
серверного согласования. Автоматическая выдача полных прав при отсутствии
scopes/capabilities или скрытый переход на старый API запрещены.

## Передача в проект dzen.chat

Пользователь поручил открыть отдельный диалог для серверной части. Переданы
описанный сценарий, группы методов, требования к статусу проекта, одноразовому
обмену, изоляции, lifecycle и проверкам. Серверная постановка должна находиться
в `docs/specs/2026-09-09-wordpress-integration-api.md` в выделенном worktree.

Скрытие и источники истории переданы в [issue #14](https://github.com/xen/dzen.chat/issues/14).
Перед реальным подключением требуется реализовать этот контракт на сервере и
проверить обмен, подпись и DTO совместно. Тестовый API в `tests/api-fixture.php`
проверяет поведение клиента и исключается из ZIP; он не является готовым Dzen API.

## Точный формат подписи клиента 0.1.0

Все серверные запросы выполняются PHP, секрет остаётся в WordPress. Заголовки:
`X-Dzen-Auth-Version: 1`, `X-Dzen-Client-Id`, `X-Dzen-Timestamp` (Unix seconds),
`X-Dzen-Nonce` (48 hex chars), `X-Dzen-Signature` (hex HMAC-SHA256).
Для изменений также передаётся `Idempotency-Key`. Обмен кода не имеет подписи
клиента и защищён code/verifier/callback. Сервер проверяет TTL времени и nonce.

Строка подписи, UTF-8, LF между строками, без LF в конце:

```text
DZEN-HMAC-V1
{UPPERCASE HTTP METHOD}
{/api/v1/path?canonical_query}
{client_id}
{timestamp}
{nonce}
{idempotency_key_or_empty}
{lowercase_hex_sha256_of_exact_body_bytes}
```

Query сортируется по имени байтовым порядком; кодирование RFC 3986, без повторных
ключей. Тело GET пустое. JSON отправляется UTF-8 без экранирования Unicode и `/`;
подписываются точные отправленные байты, сервер не пересериализует JSON.
Подпись метода, пути, тела и состояния проверяется в `tests/contracts.php`.
Никакие cookies администратора не отправляются в API.

Ответ `/integration` включает `site_url`, `integration.id/status`,
`project.id/title/status/reason_code`, `scopes` и `allowed_operations` с boolean
`widget_answers`, `documents_upsert`, `documents_delete`. Сайт, проект и
интеграция должны точно совпасть с сохранённым результатом обмена.
Ответ отзыва — JSON 200, например `{"disconnected":true}`.

Виджет: `id`, `code`, `name`, `is_enabled`, `version`, `welcome_messages`.
PATCH использует `expected_version`. Создание с `site_source_only:true` выбирает
только источник текущего сайта. В `document-events` допускается `trigger_policy`
(inherit/enabled/disabled); сервер применяет её и до появления документа в индексе.
Самостоятельный PUT политики принимает `{"mode":"disabled"}` и возвращает mode.
